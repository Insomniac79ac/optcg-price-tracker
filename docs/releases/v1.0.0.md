## Summary

First stable release of the OPTCG price tracker. Phases 1-10 delivered the full feature set below;
Phase 11 was a release-candidate audit and bug-bash pass over that work - no new product features,
no formula changes, no scraping behavior changes. See `docs/release_candidate_report.md` and
`docs/release_blockers.md` for the full readiness record, and `CHANGELOG.md` for the itemized
history.

## Major capabilities

- **Collection tracker** - per-card quantity, condition, purchase price/date/source, target sell
  price, status (hold/watch/sell/sold/grading), tags, groups, and CSV import/export.
- **Portfolio valuation** - retail/liquidation/market-floor/graded-adjusted valuation per item and
  portfolio-wide, valuation history snapshots, and best/worst performer insights.
- **Wishlist and grading workflows** - target-price wishlist tracking with CSV import/export and
  conversion to collection items; PSA/BGS/CGC/ARS/other grading submission tracking through the
  grading lifecycle, with graded value feeding back into portfolio valuation.
- **Market intelligence** - deterministic market signals (price moves, buy/sell spreads,
  floor-vs-retail gaps), persistent signal events with a review workflow, opportunity scoring,
  generated market intelligence reports, and a Telegram digest.
- **Analytics and decision support** - buy/sell decision support, grading ROI analytics, portfolio
  risk analytics, and an analytics digest.
- **Catalog import/export** - card catalog CSV import/export with validation previews before any
  real import is committed.
- **Source candidate matching and source mapping quality review** - SNKRDUNK candidate matching
  workflow and a source-mapping quality review page for catching bad or low-confidence matches.
- **Duplicate card merge tooling** - a guided, confirmation-gated workflow for merging duplicate
  catalog entries.
- **Import validation** - a dedicated preview step that reports row-level errors on a CSV before
  any data is actually imported.
- **Catalog coverage and price source health** - dashboards for tracking which cards have price
  data, from which sources, and how stale or reliable each source is.
- **TCG Vault interface** - a consistent design system (`docs/interface_design_system.md`) applied
  across every route in the app.
- **Saved views** - create, apply, set-default, and delete filter/sort presets across list and
  analytics pages.
- **Collection vault** - a dedicated, richer view of the collection distinct from the plain list.
- **Command palette** - a Ctrl/Cmd+K palette for fast navigation and workflow shortcuts.
- **Production hardening** - security headers, admin-token and per-user JWT auth, per-IP rate
  limiting, secret redaction in logs, and startup env validation (hard-fails in production on a
  weak/default `ADMIN_TOKEN`, default DB password, etc.).
- **Backup/restore** - full JSON export/import (merge or replace mode) with internal-consistency
  validation, plus automated gzipped Postgres backups with retention pruning.
- **Release audits** - `scripts/release_candidate_audit.sh` and `scripts/final_audit.sh` as
  repeatable, single-command gates for release readiness, backed by `docs/release_checklist.md`,
  `docs/release_candidate_report.md`, and `docs/release_blockers.md`.

## Admin/data safety notes

- All destructive or "real" admin actions (card-catalog import, duplicate merge, backup restore,
  cache clear, data-retention prune, job-lock force-release) require typing a confirmation phrase
  via `ConfirmActionModal` - none run on a single click or a bare `window.confirm()`.
- The admin token (`X-Admin-Token`) is only ever persisted through `getAdminToken`/`setAdminToken`/
  `clearAdminToken` in `apps/web/src/lib/api.ts`; no saved view or recent-workflow payload stores
  it, and no `localStorage` key persists confirmation text.
- `scripts/check_secrets.sh` gates every release: no tracked `.env`-style files, no committed
  backup dumps or file-job outputs, no literal secret values outside example files.
- Backup export/validate/restore-dry-run are exercised by the release-candidate audit on every run;
  a real (non-dry-run) restore should still be exercised manually at least once in a disposable
  environment before relying on it in production - see `docs/operations.md`'s backup/restore drill.

## Known limitations

- SNKRDUNK automated discovery may be blocked by site protections. When it is, use manual CSV
  import instead of trying to work around the block - this app does not bypass website
  protections and does not add SNKRDUNK live scraping.
- Analytics and decision-support output (buy/sell signals, opportunity scoring, grading ROI,
  portfolio risk) is deterministic and rules-based. It is not financial advice.
- This is a single-user/local-admin style app - there is no multi-user auth system beyond the
  per-user JWT (Google sign-in) and the shared admin token.
- There is no automatic buy/sell execution - all trading decisions and actions remain manual.

## Upgrade/deployment notes

- Run `docker compose exec api alembic upgrade head` (or `make prod-migrate` in production) after
  deploying this version - see `docs/deployment.md` and `docs/release_checklist.md` section C.
- No `.env`/`.env.production` variable names changed in this pass; existing deployments do not
  need new environment variables to upgrade to `1.0.0` from `1.0.0-rc.1`.
- If port `3000` is already in use by another stack, the dev compose file supports
  `WEB_PORT=<port>` to publish the web container on an alternate host port without touching
  production - see `docs/release_candidate_report.md`.
- Follow `docs/release_checklist.md` sections A-G (and the final tag checklist in section H) for
  the full pre-release/build/deploy/rollback sequence.

## Post-release monitoring checklist

- [ ] `GET /admin/system-check` reports `status: "ok"` (or only expected warnings) shortly after
      deploy.
- [ ] `GET /admin/release-status` shows the expected version/git commit/build time.
- [ ] `/admin/logs` has no new critical errors in the first 24 hours.
- [ ] The scheduled market workflow (refresh -> snapshot -> report -> digest) completes at least
      one run on schedule - check `/admin/refresh-runs` and the Telegram digest if configured.
- [ ] `/admin/price-source-health` shows sources refreshing as expected (no source silently gone
      stale).
- [ ] A fresh automated backup exists (`GET /admin/db-backups` or `/admin/backup`) within the
      expected retention window.
- [ ] No unexpected spike in rate-limit rejections (`/admin/performance` or logs) that would
      indicate real traffic being blocked.

# Public UX Market Value A0 — methodology and data contract audit

**Decision:** Design the new Market around a **one-copy-per-physical-CardPrint JPY basket**. Publish the literal sum as **Current tracked value**, with priced/eligible coverage beside it. Derive price movement from a separate, monetary-weighted, comparable-constituent chain. Do not label a coverage-neutral historical point as the literal market value that Atlas observed on that past day. PR #18 is an open, unmerged reference for the old direction only.

**Audit boundary:** Repository inspection and staging reads only, 2026-09-26 UTC. Each staging connection began `REPEATABLE READ READ ONLY`, verified `transaction_read_only = on`, then rolled back and closed. Alembic revision was `c4e9a2b7816d`. No source refetch, replay, job, database write, configuration change, or PR change was made.

## 1. What CPI measures now

The frozen v1 [methodology](../card_pirate_index.md) and [estimator](../../services/api/app/services/card_pirate_index.py) agree: CPI is a **dimensionless equal-weight geometric return index** starting at 1000. On adjacent available snapshot days, a print qualifies only if it has a non-null JPY value at both endpoints, the same `(index_version, source_semantics_version)` pair, and the same contributing `(source, reference_type)` set. The step is the arithmetic mean of per-print log price ratios after an unconditional cap of `±ln(1.25)`; the previous level is multiplied by `exp(step)`. This limits an upward print return to +25% and a downward print return to -20%. Entrants and leavers contribute no return; contributor churn excludes that print; a version boundary carries the level without a cross-version return; mixed-version days are unpublishable. Below 30 comparable prints, the point has a null level. Snapshot gaps are marked. Thus a ¥100 print and a ¥100,000 print have **identical weight in the return calculation**. CPI is valid for its defined question, but it is neither a monetary total nor the price movement of a one-copy basket.

The [point model](../../services/api/app/models/card_pirate_index_point.py) stores one row per `(scope_kind, scope_key, methodology_version, point_date)`, with `overall/set/rarity`, `Numeric(12,4)` index level, source/index versions, prior date, chain log return, constituent and eligible counts, cap/mover counts, break state, and carry reference. The [writer](../../services/api/app/card_pirate_index_writer.py) defaults to the overall seed from 2026-09-03. Staging contains **23 overall points, 2026-09-03 through 2026-09-25, and zero set or rarity points**. `SCOPE_SET` is groundwork: archive replay can accept a filtered print ID list, but the scheduled writer's generic `SeedSpec` does not resolve or apply release membership and currently loads the whole archive. Merely changing its scope key would mislabel overall data. The documented set key uses `COALESCE(ReleaseProduct.official_code, CardPrint.release_product_code)`; the new contract should key by authoritative `release_product_id`, including uncoded products. Existing CPI uniqueness can distinguish multiple string scope keys, but its 1000 base, field semantics, and constraints cannot represent the proposed JPY basket.

## 2. Physical identity, current JPY value, and coverage

Basket unit: **one copy of each active, verified, Japanese physical `CardPrint` with a usable current Atlas Market Index JPY value**. Each base, parallel, alternate artwork, and reprint is a separate constituent. A canonical-card basket would silently choose or merge distinct prices and could not assign a reprint to its actual product. Staging has **4,316** such active physical prints across **2,710** canonical cards, a difference of **1,606** print identities. For example, `ST01-010` Franky base and its `p1` alternate are distinct verified prints in distinct `ReleaseProduct` records; neither should erase the other. Each print contributes at most once even when multiple sources price it: the input is its single `index_value_jpy`.

The read-only live resolver evaluated 647 prints with market-facing observations at **2026-09-26 16:12:25 UTC** using Market Index version 3/source semantics 2; 639 had a usable value. These are **tracked one-copy sums, not estimates of all unpriced cards or the economic size of the global market**:

| Scope | Current tracked value | Priced / active physical prints | Coverage |
| --- | ---: | ---: | ---: |
| Overall | **¥262,279** | 639 / 4,316 | 14.8% |
| OP-05 (`ReleaseProduct.id=174`) | **¥480** | 4 / 154 | 2.6% |
| OP-17 (`ReleaseProduct.id=186`) | **¥14,780** | 20 / 169 | 11.8% |

The most recent immutable daily archive, **2026-09-25**, instead totals ¥265,539 overall, ¥480 OP-05, and ¥14,780 OP-17, with the same priced counts. The ¥3,260 live/archive difference illustrates why headline and chart require separate `as_of` timestamps. The live sum is a truthful sum of **the prices Atlas can currently value**, but OP-05's ¥480 cannot truthfully be presented as the full release's worth. Suppress an unqualified release headline and performance where coverage or comparable-panel quality fails the future publication gate.

Membership is `CardPrint.release_product_id`, never `card_code` or original-set code. Staging `EB04-007` has base/p1 prints in EB-04 (`id=173`) and a `p2` print in OP-17 (`id=186`); the latter belongs to OP-17's basket if priced. These three currently have no usable archived value. `CardPrint`'s verified identity constraint requires a release product and official asset variant, and the archive has zero missing print FKs and zero archived prints whose current release join is null.

## 3. Historical archive and the coverage trap

The append-only [MarketIndexSnapshot model](../../services/api/app/models/market_index_snapshot.py) has one `(card_print_id, snapshot_date)` row, `index_value_jpy`, calculation time, index/source-semantic versions, and JSON provenance. There are **36 archived days, 2026-08-21 through 2026-09-25**. Version 2/1 and 3/2 priced rows contain the contributor-role evidence needed for strict comparison; version 1/1's 287 priced rows lack that role flag, so contributor continuity cannot be proven there. The archived print IDs can be joined to current `CardPrint.release_product_id` with no source refetch or identity rewrite. Therefore **a historical OP-05 raw basket is computable now under today's authoritative catalogue membership**. It first has one priced print on 2026-09-24 and four on 2026-09-25; no honest 7D/30D OP-05 performance exists yet. For fully frozen as-published release history, current mutable catalogue membership is insufficient: future daily points should record the release identity or an immutable membership revision and define how corrections affect already published points.

One observed overall step shows the raw-sum error:

| 2026-09-13 → 14 | Amount |
| --- | ---: |
| Raw daily sum | ¥256,659 → ¥272,049 (**+¥15,390; +6.0%**) |
| Newly priced prints | 237 prints, **¥15,380** of the increase |
| One common print with contributor churn | Excluded from comparable movement |
| Stable comparable panel | 378 prints, ¥255,609 → ¥256,129 (**+¥520; +0.20%**) |

On 2026-09-24 → 25, nine entrants added ¥960 while one leaver removed ¥1,200; the raw sum rose ¥900 although stable common prints rose ¥1,140. On 2026-09-02 → 03, the raw sum rose ¥29,652 across a version change, but **zero** print returns were comparable across that boundary. A chart must not call any of these coverage/version effects a market rally. Source changes are also material: equal source counts do not establish equal contributor identities. Conversely, 2026-09-15 → 16 had 616 common prints, no entry/exit or contributor churn, and a ¥28,519 raw/comparable fall; coverage protection must preserve genuine observed movement.

## 4. Candidate methods and recommendation

| Method | Today's literal sum? | Coverage-neutral history? | Expensive prints get more influence? | Reproducible from archive? | Collector meaning |
| --- | --- | --- | --- | --- | --- |
| A. Raw daily `SUM(value)` | Yes | **No**; entries/exits jump | Yes | Yes, subject to membership policy | Simple value, misleading change |
| B. Scale equal-weight CPI to JPY | Only at a chosen anchor | Yes for its rules | **No** | Yes for its seeded segment | Currency label masks equal weighting |
| C. Chain comparable one-copy monetary baskets | Yes for a separate current sum; historical JPY requires anchoring | **Yes**, with quality/version breaks | **Yes** | Yes where role evidence exists | Clear price performance |
| D. Divisor-adjusted monetary aggregate | At today's endpoint only if rebased; otherwise level is `sum/divisor` | **Yes**, with explicit divisor resets | **Yes** | Yes if divisor/changes persisted | Harder to explain; same semantic trade-off |

**Recommend C as the return estimator**, with D only if a persisted normalized value line is later needed. For scope `s`, let `C(s,P,D)` be physical prints valued at both adjacent archived dates, in that scope, with identical index/source-semantic versions and contributing source identities. Then

`step_ratio = SUM(value_jpy on D for C) / SUM(value_jpy on P for C)`.

This is a monetary-weighted one-copy basket: a ¥100,000 print's ¥1,000 change affects the basket more than a ¥100 print's ¥1 change. An entrant starts contributing only after it has a comparable prior value; a leaver contributes no step. Do not silently cap returns as CPI does, since clipping breaks reconciliation to basket yen changes. Instead detect suspect outliers, surface contributor concentration and comparable-value share, and withhold a step pending defined quality rules. A zero denominator, too few comparable prints, weak value share, large single-print dominance, mixed versions, or unsupported version boundary yields **unavailable/break**, never 0% or a fabricated carry. Calibrate and publish those gates before implementation; the current four-print OP-05 panel fails any credible broad-release claim.

**Two product concepts are necessary.** Literal current sum can be displayed at its own timestamp. Chain-linking the step ratios yields coverage-neutral **price performance**. A JPY line made by anchoring that chain backwards to today's sum ends at today's literal value, but past points are *modeled comparable-basket values*, can restate when the anchor changes, and are not the literal sums Atlas recorded then. A divisor method has the same limitation. No single time-consistent series can be both the literal sum on **every date** and free of jumps when membership changes. The future `[Value]` chart must disclose modeled/backcast semantics; `[Performance]` can show the cleaner percentage chain. Keep the live headline and last archived chart point separately dated until an explicit, comparability-checked intraday bridge exists.

## 5. Page and contract consequences

- **Release scope:** use `release_product_id` FK for both raw sum and comparable panel. Overall is its own scope. Do not use original-set code; include uncoded products. Future `Compare releases` rebases each valid release performance series to 0% at the requested window start, requires a common comparable date span, and exposes gaps/version breaks. The archive can feed this after release series creation, but OP-05's present history cannot support 7D/30D.
- **Movers:** archived per-print values support gainers/losers for Overall or a release. Rank raw percentage moves separately from monetary market impact. For comparable panel `C`, show each print's `ΔJPY`, and `impact_percentage_points = 100 × ΔJPY / SUM(prior values for C)`; their signed sum reconciles to the monetary step percentage before display rounding. The existing [CPI movers](../../services/api/app/services/card_pirate_index_movers.py) use capped `log_return/n` and `approx_index_points`; those are **wrong for this basket**. Excluded/unpriced prints cannot have a comparable mover result.
- **Most valuable:** existing `GET /prints?release_product_id=…&price_basis=market_index&sort=index_desc` can list priced physical prints and supports Overall without the release filter. It computes live values and paginates. A synchronized market page should supply an `as_of`/snapshot-aligned ranking or explicitly mark this list live, rather than imply it reconciles to a different daily basket timestamp.
- **Release table:** 59 of 65 verified Bandai JP release products are dated; all 59 have active verified prints, but only **21** have any priced print at the last archive date and **9** have at least 30. A table with release, current tracked JPY sum, priced/total counts is feasible now, with explicit insufficient-coverage state. `7D`/`30D` stay null until each release passes the same comparability and span rules; do not derive them from raw sums.
- **FX:** no authoritative FX feed/service was found in the backend or web app. Store and calculate JPY. Recommend **JPY only** for A0. A later current USD headline requires a sourced, timestamped exchange rate and must be labeled approximate. Applying one current FX rate uniformly to a JPY chart changes only the display unit, not the shape; applying historical daily rates adds USD/JPY movement and must be labeled an FX-adjusted view.
- **Persistence/API:** introduce a separate versioned daily monetary-basket point contract keyed by `overall` or FK `release_product_id` plus UTC date/methodology version. Persist raw JPY sum, priced and eligible print counts, comparable prior/current JPY sums and count, ratio/chain or divisor state, version pair, contributor/coverage exclusions, concentration/quality state, break reason, and immutable release-membership basis. Keep input snapshot IDs or a deterministic archive fingerprint for replay verification. Serve current headline with timestamp/coverage; historical value/performance with semantics and gaps; rebased release comparison; release table; monetary movers; aligned most-valuable prints. Existing CPI point fields must not be repurposed. **A migration is required for durable public monetary series**; a read-only prototype can compute from existing archives without one. No past `market_index_snapshots` may be fabricated or rewritten.
- **Future page:** “One Piece Market” leads with *Current tracked market value* and valid 7D/30D movement, All One Piece/Release selector, `[Value] [Performance]` branded chart, compare releases, market movers, release table, most valuable prints, then collapsed **Data & methodology**. Do not prioritize the generic `1000.xx` level, “Market snapshot,” median price, price band, catalogue coverage cards, or arbitrary “Cards in this market.” Coverage remains visible as quality context. Every primary chart needs a clearly visible CardPirate Atlas compass/wordmark, `cardpirateatlas.com` where appropriate, legible in screenshots and exported images without obscuring data.

**Smallest safe implementation sequence:** (1) freeze and test the basket eligibility, release membership, version/contributor, quality, and current-vs-history semantics against immutable archive fixtures; (2) add the separate persistence contract/migration and read-only deterministic replay/verification for historical derived points, without source refetch; (3) add forward daily monetary points and API contracts, then validate timestamp reconciliation, sparse releases, breaks, and movers; (4) build the replacement page and screenshot/export watermark after the contracts pass. PR #18 stays open and unmerged until the new direction is implemented separately.
